### 完全自動ワークフロー（0:30-3:00）

最初のテンプレートは「完全自動ワークフロー」です。

```markdown
---
inclusion: manual
---

# 完全自動ワークフロー

`#full-auto` で呼び出された場合、以下のルールで作業を進める。

## 基本方針
- **質問しない**。memoと既存コードから推論する
- **承認を求めない**。必要な作業はすべて実行する
- **完了まで止まらない**。エラーが出たら自力で修正する

## 情報の取得先
1. `memo/memo.YYYYMMDD.md` で当日のタスクを確認
2. 前回のコミット履歴で作業の続きを把握
3. 既存コードのパターンに従う

## 作業完了の定義
- コードが動作する状態
- テストがパスする
- lintエラーがない
- PRが作成されている（push可能な場合）

## エラー時の対応
- ビルドエラー → 修正して再試行（最大3回）
- テスト失敗 → 失敗内容を分析して修正
- 3回試行しても解決しない → その時点での状態を報告して停止
```

このテンプレートを `full-auto-workflow.md` として保存します。

使い方は `#full-auto 作業を進めて` です。

### リポジトリ調査モード（3:00-5:30）

2つ目は「リポジトリ調査モード」です。

巨大なリポジトリを調査するときに使います。

```markdown
---
inclusion: manual
---

# リポジトリ調査モード

`#investigate` で呼び出された場合、以下のルールで調査を進める。

## 基本方針
- **質問しない**。調査対象を自分で判断する
- **網羅的に調べる**。関連しそうなファイルはすべて確認する
- **レポートにまとめる**。調査結果は構造化して出力する

## 調査の進め方
1. まずディレクトリ構造を把握する
2. エントリーポイント（main, index, app）から追跡する
3. 依存関係を再帰的に辿る
4. 設定ファイル（config, env, yaml）も確認する
5. テストコードからも仕様を読み取る

## レポートの形式
調査完了後、以下の形式でレポートを出力する：

### 1. 概要
- 対象機能の目的
- 主要なファイル一覧

### 2. アーキテクチャ
- データフロー
- 依存関係

### 3. 重要な実装詳細
- 核となるロジック
- 注意すべき点

## 出力先
- 調査結果は `memo/investigation-YYYYMMDD-{対象}.md` に保存
```

このテンプレートを `investigate-repo.md` として保存します。

使い方は `#investigate 認証周りの実装を調査して` です。

### 表現の強度（5:30-6:30）

Steeringの表現には「強度」があります。

弱い表現だと、Kiroは無視することがあります。

**NG: 弱い表現**
- できれば質問せずに進めてください
- 可能であれば自動で実行

**OK: 強い表現**
- **質問は禁止**。不明点は推論で補う
- 確認が必要な場合でも、まず実行してから報告する

強い表現を使うことで、確実に指示が通ります。

### カスタマイズのヒント（6:30-7:30）

テンプレートは、自分のワークフローに合わせてカスタマイズしてください。

よくあるカスタマイズ例：

**メモの場所を変える**
```markdown
## 情報の取得先
1. `docs/daily/YYYYMMDD.md` で当日のタスクを確認
```

**テストコマンドを指定する**
```markdown
## テスト実行
- Node.js: `npm run test`
- Python: `pytest`
- Go: `go test ./...`
```

**禁止コマンドを追加する**
```markdown
## 禁止事項
- `rm -rf` は実行しない
- `git push -f` は実行しない
- 本番DBには接続しない
```
